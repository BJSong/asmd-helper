# 저장 계약과 검증 기준

## 설계 결정

현재 앱은 개인용 단일 저장 공간이다. IndexedDB와 Supabase 모두 `AppState` 전체를 한 개의 스냅샷으로 저장한다. Supabase의 유일한 학습 데이터 테이블은 `public.app_state`다. `data`가 학습 기록의 기준이고 `revision`이 동시 수정 방지용 버전이다. 앱은 별도의 SQL 학습 테이블을 읽지 않는다.

초기 설계는 스냅샷과 파생 SQL 테이블을 동시에 저장했다. 답안 하나를 저장할 때 모든 파생 행을 삭제하고 재생성했기 때문에, 앱에서 허용한 기록도 파생 테이블의 별도 제약 때문에 저장이 실패할 수 있었다. `202610160001_single_state_contract.sql`은 이 중복 저장을 제거한다. 이전 파생 테이블은 `asmd_legacy` 스키마로 옮겨 기존 내용을 보존하지만, 앱은 더 이상 읽거나 쓰지 않는다. 기존 DB에는 적용 전에 백업을 만든다.

## 불변조건

1. 앱 모델은 `shared/model.ts`의 `stateSchema`로 검증한다. SQL은 현재 `schemaVersion = 2`를 받고 `data.revision = app_state.revision`을 강제한다.
2. 빈 DB에서 첫 저장은 `expected_revision = 0`만 허용한다. 이후 저장은 DB의 현재 revision과 기대 revision이 같을 때만 성공한다. 실패한 저장은 기존 상태를 바꾸지 않는다.
3. 최초 답안, 재시도, 세션 복습, 간격 복습, 계획, 설정은 모두 `data` 안에 보존한다. 특정 기록을 별도 테이블에서 조회하지 않는다.
4. `anon`과 `authenticated`는 테이블과 저장 함수에 접근할 수 없다. 서버만 server secret 키로 접근하고, 서버 API는 가족 암호 로그인으로 발급한 서명된 HttpOnly 세션 쿠키를 검사한다.
5. 로컬과 클라우드 저장소는 자동 동기화하지 않는다. JSON 백업·복원은 같은 `AppState` 모델을 사용한다.

## 자동 검증

`npm test`는 PGlite에서 모든 마이그레이션을 실제 실행하고, 앱 도메인이 만든 상태의 왕복 저장, 같은 밀리초 재시도, 세션·간격 복습, 기존 v1·v2 DB 업그레이드, 초기/이후 revision 충돌, 익명 접근 거부를 검사한다. `npm run typecheck`는 앱과 서버의 타입을 검사한다.

이 검사는 로컬 PostgreSQL 호환 엔진을 사용한다. 실제 Supabase 프로젝트의 API, 키, 배포 환경은 별도로 연결한 뒤 통합 검증해야 한다. 현재 저장소는 Supabase 프로젝트에 스키마를 적용하거나 외부 서비스를 배포하지 않는다.

## 실제 Supabase 연결 전 확인

- 새 테스트 프로젝트에서 세 마이그레이션을 순서대로 적용하고, `public.app_state`만 앱의 쓰기 대상인지 확인한다.
- 기존 v2 DB를 시험할 때는 백업 후 세 번째 마이그레이션을 적용하고, `asmd_legacy`에 이전 파생 행이 남는지 확인한다.
- 서버 API로 최초 저장, 일일·자유 학습, 재시도, 두 종류의 복습, 백업·복원, 삭제와 재시작을 실행한다.
- 같은 revision의 동시 저장에서 한 요청만 성공하고 다른 요청은 409인지 확인한다. `anon`/`authenticated`로 직접 읽기·함수 호출이 거부되는지 확인한다.
- 브라우저 번들에 Supabase 서버 키가 없는지 확인하고, 로그인 세션 없이 서버 API가 401 또는 503을 반환하는지 확인한다.

백업 가져오기와 클라우드 요청은 현재 10MB 제한이 있다. 장기간 기록의 용량과 응답 시간은 실제 서비스 조건에서 별도 측정이 필요하다.
